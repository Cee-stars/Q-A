# 質問応答ドリル アプリ 計画書

> チェックリスト項目名: **質問応答（Q10音読→3問回答→1問添削）**

---

## 1. これは何か

毎日8分、スマホで声を出す英語スピーキング・ドリルの**進行役**。
既存の「質問応答」練習を置き換え、週2〜3回から**毎日**に上げるためのもの。

### 設計の憲法（迷ったらここに戻る）

1. **アプリはタイマー付きの台本であって、学習プラットフォームではない。**
   声を出す前のタップが1つ増えるのは、機能追加ではなくバグ。
   目標: 開く → 1タップ → **5秒以内に喋り始めている**。
2. **合計8分を絶対に超えない。** 各工程はハードタイマー。工程を増やすときは何かを削る。
3. **喋っている間、画面を見ない。** 工程の切り替えは音とバイブで伝える。
4. **途中で止まってもよい。** どこまでやったかが必ず残る。
5. **待ち時間を作らない。** API を待って無音になるくらいなら、キャッシュした昨日の素材を使う。

## 2. 1回のセッション（合計 6分15秒 ＋ 余白）

| # | 工程 | 時間 | 画面 | ユーザーの操作 |
|---|------|------|------|----------------|
| 1 | 生成 | **0秒** | （なし） | なし。前夜に先読み生成済み |
| 2 | Q10 音読 | 60秒 | 10問を一覧表示、6秒ごとに現在行がハイライト | なし |
| 3 | 3問回答 | 45秒 × 3 = 135秒 | 大きなカウントダウンリング＋質問文のみ | なし（**一時停止ボタンは置かない**） |
| 4 | 1問添削 | 120秒 | 3問から1つタップ → 録音 → 文字起こし → 添削文 | タップ1回、喋る |
| 5 | 3回音読 | 60秒 | 添削文を特大表示、20秒ごとにチャイム | なし |

**合計 375秒 = 6分15秒。** 残り約1分45秒は起動・遷移・遅延の吸収に使い、**工程を増やさない**。
（8分を守れることが、毎日続く唯一の理由。空いた時間で4問目を足したくなるが、Phase 4 まで我慢する。）

### 各工程の設計判断

**工程2（Q10音読）** — 1問6秒。「考えず口だけ動かす」の速度をアプリ側が強制する。
自動スクロール／ハイライトで、次を探す視線移動をなくす。

**工程3（3問回答）** — どの3問をやるかは**アプリが自動で選ぶ**。
選ばせると考える時間が発生し、それは声を出す時間ではない。
選定ロジック: 未回答 > 直近で詰まった系統 > ランダム。気に入らなければスワイプで1回だけ差し替え可。
「詰まっても止めない」を守るため、**この工程には一時停止も次へボタンも無い**。45秒は必ず経過する。

**工程4（1問添削）** — 直前の3問がボタンとして並ぶので、一番言えなかったものをタップ（1タップ）。
その場でもう一度マイクに向かって答える → 文字起こし → 添削。
API の待ち時間（3〜8秒）は無音にせず、「息を整える」表示＋前回の添削文を出しておく。

**工程5（3回音読）** — ハンズフリー。20秒 × 3 のチャイム。読み終わりを自己申告させない。

**小声モード** — 周囲に人がいる日用。声を出さず口だけ動かす。記録上は同じ1回として扱う。
（工程2がもともと「口だけ動かす」なので、この発想は既存手順と整合する。）

## 3. 記録（「どこまでやったか」が残る仕組み）

1日1行。行のラベルは指定どおり **`質問応答（Q10音読→3問回答→1問添削）`**。
その下に工程1〜5のドットを並べ、到達した工程まで塗る。

```
9/10  質問応答（Q10音読→3問回答→1問添削）   ●●●●●   完了
9/09  質問応答（Q10音読→3問回答→1問添削）   ●●●○○   3問回答まで
9/08  質問応答（Q10音読→3問回答→1問添削）   ●●●●●   完了
```

途中で閉じてもその時点までが保存される（工程が変わるたびに書き込む）。
連続日数（ストリーク）は表示するが、途切れても赤くしない。罰は継続の敵。

保存するもの: 日付 / 到達工程 / 出題10問 / 回答した3問 / 選んだ1問 / 文字起こし / 添削文。
**添削文の蓄積が、このアプリの長期的な資産**（Phase 4 で再利用する）。

## 4. 技術構成

| 領域 | 選択 | 理由 |
|------|------|------|
| 形態 | PWA（ホーム画面に追加） | 1コードベース、即日反映、あとで iOS 化も可能 |
| ビルド | Vite + TypeScript | 起動の速さが体験そのもの。バンドルは小さく保つ |
| UI | Preact（約3KB）＋ 小さなステートマシン | 画面は実質1つ。フレームワークを厚くする理由がない |
| 保存 | IndexedDB（`idb-keyval`） | 音声とセッション履歴。オフラインで完結 |
| 配信 | GitHub Pages | 無料・HTTPS（マイクに必須）・このリポジトリから直接 |
| 生成/添削 | Claude API を**ブラウザから直接** | 個人利用1人。サーバーを立てない |
| 文字起こし | Web Speech API →（不安定なら）STT API | 下記の注意を参照 |

### 配色

明るい紙の色。**純白 (#FFFFFF) は使わない** — 長時間の読みで眼精疲労が大きく、
暖色寄りのオフホワイトのほうが読みやすいという結果が各所で一致している。
文字も純黒にせず暖かいチャコールにする（黒＋白はちらついて見える）。

| 用途 | 値 |
|------|-----|
| 背景 | `#faf6ef` 黄味を抑えた紙色（Kindle のセピア `#fbf0d9` は黄味が強くオレンジと干渉する） |
| 面（現在行・入力欄） | `#f2ebe0` |
| 本文 | `#2c2724` 暖かいチャコール |
| 補助 | `#6b6055` |
| アクセント（図形・ボタン） | `#b0451d` |
| アクセント（小さい文字） | `#8f3a19` |

明るい背景では、もとのオレンジ `#e8734a` はコントラスト比 2.8 で文字として読めない。
**配色を変えたら `npm run test:contrast` で比率を確認する**（小さい文字 4.5、図形 3.0 が下限）。

夜でも自動で暗くはしない。暗い画面をやめるために明るくしているので、
`prefers-color-scheme` による自動切り替えは入れていない。

### 忘れると必ず事故る2点

- **Screen Wake Lock API**（iOS 16.4+）。これを入れないと音読中に画面が消える。工程2で必ず取得し、セッション終了で解放する。
- **マイク権限は HTTPS 必須**。ローカル開発は `localhost` か `vite --https` で。

### API キーの扱い（正直な話）

ブラウザから Claude API を直接叩くため、キーは端末の localStorage に置く。
Anthropic API はそのためのヘッダ（`anthropic-dangerous-direct-browser-access`）を持っている。

- **許容できる理由**: 利用者は本人1人、キーは自分の端末から出ない、GitHub Pages 上のコードにキーは含めない（初回に手入力）。
- **許容できないケース**: 誰かに配る、端末を共有する。その時は Cloudflare Workers に薄いプロキシを1枚置く（実装30分程度）。Phase 2 の時点で差し替え可能なようにインターフェースを切っておく。
- **リポジトリにキーを絶対に入れない**。`.env` も含めてコミット対象外。

### 文字起こしの現実的なリスク

iOS Safari の `webkitSpeechRecognition` は存在するが、長め・連続の認識で不安定になることがある。
そこで**最初から3段構えにする**:

1. Web Speech API（無料・追加キー不要）を試す
2. 失敗・無音・明らかに壊れた結果 → テキスト欄にフォールバックし、**iOS 標準の音声入力**で入れてもらう
3. それでも実用に耐えなければ、設定で STT API（Whisper 互換）に切り替え

**実機での検証を Phase 3 の最初の1週間に必ず入れる。** ここは机上で決めきらない。

## 5. プロンプト設計

アプリが2つのプロンプトを所有する。**両方とも設定画面で編集可能にする**（デプロイなしで調整するため）。

### 5.1 質問生成（前夜に先読み実行）

入力: レベル / 目標（面接・雑談・会議など）/ 扱いたいテーマ / **直近30問（重複回避のため除外指定）**
出力: JSON 配列で10問。1問は音読6秒に収まる長さ（15語以内）。

制約として明記すること:
- 10問のうち 6問は易（即答できる）、3問は中、1問は難。詰まる経験を1問だけ確実に混ぜる
- 抽象論ではなく、自分の経験を語らせる質問にする
- 直近30問と意味が重ならないこと

### 5.2 添削（工程4）

入力: 質問文 + 文字起こし全文
出力を**厳しく縛る**。ここが緩むと工程5の音読60秒に収まらない。

- 直した文: **2〜4文**。話し言葉として自然に、元の内容は変えない
- 変えた箇所: **最大3つ**、各1行、理由は10語以内
- 説教・励まし・前置き・後置きは一切なし
- `max_tokens` でも上限をかける（体裁ではなく物理で守る）

## 6. 開発フェーズ

**順序の原則: 習慣を技術の完成に待たせない。** 骨格が動いた日から毎日使い始める。

### Phase 1 — 歩く骨格（これだけで練習は始められる）✅ 完了
- 5工程のステートマシンとハードタイマー、音とバイブによる工程遷移
- 種問題バンク60問を同梱（API なしで動く）
- 工程4は「テキスト欄に自分で打つ」だけ（添削なし）
- 記録の保存と1行表示、Wake Lock、PWA 化、GitHub Pages へデプロイ
- **完了条件: 通しで1回、8分以内に終えられる**

### Phase 2 — API 接続
- 設定画面（APIキー、レベル、テーマ、プロンプト編集）
- 添削の実装（工程4）
- **翌日分の先読み生成**とキャッシュ。オフライン時は種バンクへ自動フォールバック
- **完了条件: 手順1の30秒が体感ゼロになる**

### Phase 3 — 音声
- 工程4の録音 → 文字起こし → 添削への自動接続、3段フォールバック
- **実機（iPhone / Safari）で1週間の実運用検証**
- **完了条件: タップ1回と発話だけで工程4が終わる**

### Phase 4 — 復習資産
- 蓄積した添削文の一覧と、工程2の10問に過去の詰まった質問を1問混ぜる
- 統計（連続日数、総発話時間、詰まりやすいテーマ）
- ここで初めて「余った1分45秒で4問目」を検討する

## 7. リスクと対処

| リスク | 対処 |
|--------|------|
| iOS Safari の音声認識が不安定 | 3段フォールバックを最初から設計。Phase 3 で実機検証 |
| API 遅延で無音時間が生まれる | 生成は先読み。添削の待ちは前回の添削文で埋める |
| 8分を超えて続かなくなる | 合計375秒を仕様として固定。工程追加は Phase 4 以降 |
| 生成問題の重複・品質のブレ | 直近30問を除外指定、難易度配分を明示、JSON で受ける |
| 音読中に画面が消える | Wake Lock を工程2で取得（実装必須項目） |
| APIキーの露出 | 端末内保管＋リポジトリに含めない。共有するならプロキシへ移行 |
| 機能を足したくなる | この計画書の「憲法」5条を先に読み返す |
