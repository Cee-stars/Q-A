# 質問応答ドリル アプリ 計画書

> チェックリスト項目名: **質問応答（復習→3回回答→添削→定着）**

---

## 1. これは何か

毎日8分、スマホで声を出す英語スピーキング・ドリルの**進行役**。
既存の「質問応答」練習を置き換え、週2〜3回から**毎日**に上げるためのもの。

### 設計の憲法（迷ったらここに戻る）

1. **アプリはタイマー付きの台本であって、学習プラットフォームではない。**
   声を出す前のタップが1つ増えるのは、機能追加ではなくバグ。
   目標: 開く → 1タップ → **5秒以内に喋り始めている**。
2. **合計8分を絶対に超えない。** 各工程はハードタイマー。工程を増やすときは何かを削る。
3. **喋っている間、画面を見ない。** 工程の切り替えは音とバイブで伝える。
4. **途中で止まってもよい。** どこまでやったかが必ず残る。
5. **待ち時間を作らない。** API を待って無音になるくらいなら、キャッシュした素材を使う。
6. **毎日やっても効かない作りなら、続ける意味がない。**
   時間の使い方を変えるときは、第2章の根拠に照らして決める。

## 2. なぜこの形なのか（設計の根拠）

初版は「質問を10問音読 → 別々の3問に1回ずつ答える → 1問添削 → 添削文を3回音読」だった。
これは**効果の源泉を3つ取り逃していた**。作り直した理由を残す。

### 2.0 言えないものは、待っても出てこない — 全体

利用者が2日続けて「3回回答まで」で離脱した。理由は
**「質問に英語で答えられないのが多かった」**。

流暢さ育成（Nation の四つの要素）は**未知の言語材料がゼロであること**が成立条件。
言えない学習者に 45秒×3 を課しても、反復ではなく沈黙が3回起きるだけ。
**最初の設計は、利用者が持っていない言語を前提にしていた。**

→ **手本を、言い直しの前に渡す。** 全問に手本の答えを持たせ、APIキーが無くても成立させる。
→ 当面 hard は出さない（`DAILY_MIX.hard = 0`）。抽象的な問いは
　「内容の負荷」と「構文の負荷」を同時にかけるだけで、詰まる経験にならない。

### 2.1 流暢さは「同じ内容」の反復で伸びる — ただし工程5には適用できない

**4/3/2 テクニック**（Maurice 1983, Nation 1989, Arevart & Nation 1991）は、
*同じ話*を4分→3分→2分と時間を縮めて3回話す。Nation (1989) の実測で
話す速度が **86 → 100 → 127 wpm（+48%）**。内容の検索が済んでいるぶん、
注意が形と流暢さに向くのが効く理由。

初版は**違う質問に1回ずつ**答えていた。反復そのものが無いので、この効果は出ない。

**ただし、手本を挟んだ時点で 4/3/2 の根拠は使えなくなった。**
効果の源泉は「内容の検索が1回目で済んでいること」であり、
1回目が空で2回目から他人の文が入るなら、回1と回2以降は**別の内容**で、反復ではない。

→ 工程5（35/25/20）の根拠は 4/3/2 ではなく、
　**段階的な足場の除去**（worked-example fading）と検索練習に置く。
→ **本物の 4/3/2 が起きるのは工程2（復習）のほう。**
　自分の文が既知になった翌日以降、同じ内容を思い出して言うのがそれにあたる。

### 2.2 直後に3回読むのは、最も忘れる練習法 — 工程2と工程5

集中練習は初回の再生成績がほぼ完璧になるが**急速に忘れる**。
分散した検索練習は初回成績こそ劣るが、**最終テストで上回る**。
さらに読み返しは *再学習* であって *検索* ではなく、検索練習は再学習より記憶に残る。

初版の「添削文を直後に3回音読して終わり」は、集中練習かつ再学習。
**気持ちよく終われるが、最も残らない**組み合わせだった。

→ **添削文は「読み返す文」ではなく「後日もう一度答えさせられる質問」として戻す。**
　 1日後・3日後・7日後・21日後の4回（工程2）。工程5にも暗唱を1回挟む。

### 2.3 音読する材料が間違っていた — 工程2

音読・シャドーイング自体には根拠がある（ワーキングメモリ、音素知覚）。
ただし系統的レビューの指摘が重い: **統制された音読課題の成績は、実際の会話に転移するとは限らない**。

それ以上に、初版が音読していたのは**質問文**だった。
`What did you have for dinner yesterday?` を現実で言う機会はほぼない。
発声のウォームアップではあっても、学習ではない。

→ **音読する材料を、自分の過去の添削文にする。** 復習カードが足りない日だけ質問の音読で埋める。

### 2.4 訂正フィードバックの位置は正しかった — 工程4

これは初版から変えていない。訂正フィードバックのメタ分析（Li 2010）は効果を支持し、
**産出直後の即時フィードバック**が有効、**明示的フィードバックは即時・短期遅延テストで暗示的を上回る**。
「詰まった直後に、明示的に直される」は理論的に一番効く瞬間を突いている。

ただし長期遅延テストでは暗示的フィードバックのほうが効果が持続する。
**一度直されただけでは定着しない**ということで、2.2 の分散検索がその穴を埋める。

### 2.5 このアプリが埋めない枠 — インプット

8分すべてがアウトプットである。これは**意図的な限界**であって、見落としではない。

インプットが習得を駆動し、アウトプットは主に**すでに持っているものへのアクセス速度**を上げる、
というのが大枠の見方（「インプットだけで必要十分」という強い主張には議論があるが、
インプットが必要不可欠な点は争いがない）。

つまりこのアプリは**「すでに言えることを、速く・詰まらずに言えるようにする」装置**。
Nation の四つの要素で言えば**流暢さの育成**の枠を埋める。
残り3つ（意味中心のインプット／アウトプット／言語形式の学習）は**この8分の外に置く**。

**インプットをアプリに足してはいけない。** 8分を守ることが習慣の要であり、
インプットは8分に収まらない。ここを混ぜると両方が壊れる。

## 3. 1回のセッション（合計 4分 ＋ 余白）

| # | 工程 | 時間 | 中身 | 根拠 |
|---|------|------|------|------|
| 1 | 準備 | **0秒** | 前夜に先読み生成済み | — |
| 2 | 復習 | 80秒 | 過去の持ち帰りを4枚。質問だけ見て12秒思い出す → 8秒で答えを見て読む | 2.2 / 2.3 |
| 3 | 挑戦 | 20秒 | まず自力で。**言えなければ日本語でよい** | 2.0 |
| 4 | 手本 | 60秒 | 手本を受け取る。読み上げも走る。書いていれば添削もする | 2.0 / 2.4 |
| 5 | 言い直し | 35+25+20 = 80秒 | 全表示 → 書き出しだけ → 非表示 | 2.1 |

**合計 240秒 = 4分。** 8分の予算に対して余裕がある。**工程を増やさない。**

**挑戦が20秒なのは、事前テスト効果が十数秒で出るから。**
45秒にしても気づきは増えず、沈黙の時間と士気の消耗だけが増える。

**丸暗記を防ぐため、「1文目は手本のまま、2文目は自分のことに変える」と指示する。**
手本をそのまま再生する練習は、流暢さがその文にしか付かない。

### 各工程の設計判断

**工程2（復習）** — 1枚20秒。前半12秒は質問だけを見せ、**答えを隠したまま声に出させる**。
後半8秒で添削文を出し、読ませる。検索 → 即時フィードバック → 発声が20秒に収まる。

復習カードが4枚に満たない日（開始直後など）は、**残り時間を質問の音読で埋める**。
初日は全部が音読になり、初版と同じ挙動に縮退する。

**工程3（3回回答）** — 1問だけ。選ばせない。難易度は mid を軸に日ごとに回す
（毎日 hard だと45秒×3が消耗になり、毎日 easy だと詰まる経験が消える）。
「詰まっても止めない」を守るため、**一時停止も次へも無い**。

**工程4（添削）** — 3回答えた1問がそのまま来るので、**選択のタップが消えた**。
3回目は自分の最良の試行なので、そこを直されるのが一番効く。

**工程5（定着）** — 真ん中の20秒だけ文を隠す。読み返しの間に検索を1回挟むため。
本命の検索は翌日以降の工程2。

**小声モード** — 周囲に人がいる日用。声を出さず口だけ動かす。記録上は同じ1回。

## 4. 復習スケジュール

添削文は1項目につき **1日後・3日後・7日後・21日後**の4回出て、卒業する。

1日1項目増えるので、定常状態の需要は **4件/日**。工程2の枠も **4枚/日**。
**需要と容量が釣り合っている**ので、溜まり続けない（`INTERVALS.length === REVIEW_SLOTS` をテストで固定している）。

- 期限が来たものを、**遅れている順**に出す
- 枠が余ったら**卒業済みの項目**を古い順に混ぜる（枠を遊ばせない）
- それでも余ったら質問の音読で埋める

**自己採点はしない。** 「言えた／言えなかった」を選ばせると、声を出している最中にタップが要る。
そのぶん間隔は適応せず固定になる。Phase 3 で音声認識が入ったら、
言えたかどうかを自動判定して間隔を適応させる余地がある。

## 5. 記録（「どこまでやったか」が残る仕組み）

1日1行。行のラベルは **`質問応答（復習→3回回答→添削→定着）`**。
その下に工程1〜5のドットを並べ、到達した工程まで塗る。

```
9/12  質問応答（復習→3回回答→添削→定着）   ●●●○○   3回回答まで
9/11  質問応答（復習→3回回答→添削→定着）   ●●●●●   完了
```

工程が変わるたびに書き込むので、途中で閉じてもその時点までが残る。
連続日数は表示するが、途切れても赤くしない。罰は継続の敵。

## 6. 技術構成

| 領域 | 選択 | 理由 |
|------|------|------|
| 形態 | PWA（ホーム画面に追加） | 1コードベース、即日反映、あとで iOS 化も可能 |
| ビルド | Vite + TypeScript | 起動の速さが体験そのもの |
| UI | Preact（約3KB）＋ 小さなステートマシン | 画面は実質1つ |
| 保存 | IndexedDB（`idb-keyval`） | 記録と復習項目。オフラインで完結 |
| 配信 | GitHub Pages | 無料・HTTPS（マイクに必須） |
| 生成/添削 | Claude API を**ブラウザから直接** | 個人利用1人。サーバーを立てない |
| 文字起こし | Web Speech API →（不安定なら）STT API | 下記参照 |

### 配色

明るい紙の色。**純白 (#FFFFFF) は使わない** — 長時間の読みで眼精疲労が大きい。
文字も純黒にせず暖かいチャコールにする。

| 用途 | 値 |
|------|-----|
| 背景 | `#faf6ef` |
| 面（カード・入力欄） | `#f2ebe0` |
| 本文 | `#2c2724` |
| 補助 | `#6b6055` |
| アクセント（図形・ボタン） | `#b0451d` |
| アクセント（小さい文字） | `#8f3a19` |

**配色を変えたら `npm run test:contrast`**（小さい文字 4.5、図形 3.0 が下限）。
夜でも自動で暗くはしない。

### 忘れると必ず事故る2点

- **Screen Wake Lock API**（iOS 16.4+）。無いと音読中に画面が消える。
- **マイク権限は HTTPS 必須**。ローカル開発は `localhost` で。

### API キーの扱い

ブラウザから直接叩くため、キーは他の設定と一緒に端末の IndexedDB に置く
（公式 SDK の `dangerouslyAllowBrowser` でブラウザからの直接呼び出しを明示的に許可している）。

- **許容できる理由**: 利用者は本人1人、キーは端末から出ない、コードに含めない
- **許容できないケース**: 誰かに配る、端末を共有する → Cloudflare Workers に薄いプロキシを1枚
- **リポジトリにキーを絶対に入れない**

### 文字起こしの現実的なリスク

iOS Safari の `webkitSpeechRecognition` は長め・連続の認識で不安定になることがある。3段構え:

1. Web Speech API（無料・追加キー不要）
2. 失敗・無音・壊れた結果 → テキスト欄にフォールバックし、**iOS 標準の音声入力**
3. それでも駄目なら設定で STT API（Whisper 互換）

**実機検証を Phase 3 の最初の1週間に必ず入れる。**

## 7. プロンプト設計

アプリが2つのプロンプトを所有する。**両方とも設定画面で編集可能**にする。

### 7.1 質問生成（前夜に先読み実行）

入力: レベル / 目標 / テーマ / **直近30問（除外指定）**
出力: JSON 配列で10問。1問は音読6秒に収まる長さ（15語以内）。

- 10問のうち 6問は易、3問は中、1問は難
- 抽象論ではなく、自分の経験を語らせる
- 直近30問と意味が重ならないこと
- **45秒×3回話せる中身がある質問にする**（4/3/2 が成立する条件）

### 7.2 添削（工程4）

入力: 質問文 + 文字起こし全文
出力を**厳しく縛る**。緩むと工程5の60秒にも、後日の復習20秒にも収まらない。

- 直した文: **2〜4文**。話し言葉として自然に、元の内容は変えない
- 変えた箇所: **最大3つ**、各1行、理由は10語以内
- 説教・励まし・前置き・後置きは一切なし
- `max_tokens` でも上限をかける

## 8. 開発フェーズ

**順序の原則: 効果が最大の変更を後回しにしない。**
（初版の計画は分散検索を Phase 4 に置いていた。これは優先順位の誤りだった。）

### Phase 1 — 歩く骨格 ✅ 完了
- 5工程のステートマシンとハードタイマー、音・振動による工程遷移
- 種問題バンク60問、記録、Wake Lock、小声モード、PWA/オフライン

### Phase 1.5 — 学習設計の作り直し ✅ 完了
- 4/3/2（同じ1問を 45/35/25）
- 添削文の分散検索（1・3・7・21日）と、工程2の復習カード
- 工程5に暗唱を1回挟む
- **API も音声も無しで、学習設計としては完成している**

### Phase 2 — API 接続 ✅ 完了
- 設定画面（APIキー、レベル、目標、テーマ、プロンプト編集）
- 添削の実装（工程4）。失敗しても自分の文のまま工程5へ進む
- **翌日分の先読み生成**とキャッシュ。オフライン時は種バンクへ
- SDK は動的 import。初回描画のバンドルに API クライアントを含めない
- 実際に出した問題を控えて、次の生成の除外指定に渡す

### Phase 3 — 音声
- 工程4の録音 → 文字起こし → 添削への自動接続、3段フォールバック
- **実機（iPhone / Safari）で1週間の実運用検証**
- 工程2の復習で、言えたかどうかを自動判定して間隔を適応させる

### Phase 4 — 観測
- 統計（連続日数、総発話時間、詰まりやすいテーマ、復習の滞留）
- ここで初めて余った時間の使い道を検討する

## 9. リスクと対処

| リスク | 対処 |
|--------|------|
| 毎日やっても効かない作りになる | 第2章の根拠に照らして時間配分を決める。惰性で工程を足さない |
| 復習が溜まって終わらなくなる | 需要4件/日 = 枠4枚/日 で釣り合わせ、テストで固定 |
| 同じ1問を3回が退屈になる | 回ごとに時間を縮め、目標を変える。難易度は日ごとに回す |
| iOS Safari の音声認識が不安定 | 3段フォールバック。Phase 3 で実機検証 |
| API 遅延で無音時間が生まれる | 生成は先読み。添削の待ちは前回の添削文で埋める |
| 8分を超えて続かなくなる | 合計365秒を仕様として固定。テストで検証 |
| 音読中に画面が消える | Wake Lock を工程2で取得 |
| APIキーの露出 | 端末内保管＋リポジトリに含めない |

## 10. 現在地

Phase 2 まで実装済み。生成の先読みと添削が動く。次は Phase 3（音声）。

**API の失敗は練習を止めない。** 生成が落ちれば種問題バンク、添削が落ちれば
自分の書いた文がそのまま工程5と復習に流れる。オフラインでも1回ぶんは成立する。

インプットはこのアプリの外に置くこと（2.5）。この8分だけでは、
言えることが速くなるだけで、言えることは増えない。
